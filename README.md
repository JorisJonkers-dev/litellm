# litellm

LiteLLM for the JorisJonkers-dev estate: `ghcr.io/jorisjonkers-dev/litellm`, the one proxy the estate's cheap agents reach their models through. Each agent id gets its own virtual key, restricted to its models and capped with a hard budget (agent-kit#454).

## The image

- `Dockerfile` pins the LiteLLM base by tag and digest. Renovate bumps both.
- `config/config.yaml` is the route list, copied into the image so no deployment mounts configuration. It holds three things: an `include` of `models.generated.yaml` (the deployments the catalogue sync generates), a `credential_list` with one entry per account, and a flat catch-all wildcard per account so an id the catalogue has not deployed yet still reaches its provider.
- `config/models.generated.yaml` is generated. It is a JSON document under a comment header, which is valid YAML, and it starts empty.

| Route (credential) | Provider | Upstream key (Vault field) | Plan |
|---|---|---|---|
| `vibe` | Mistral, Vibe plan | `vibe_api_key` | EUR 255 a month |
| `vibe-study` | Mistral, Vibe study plan | `vibe_study_api_key` | EUR 127.50 a month |
| `vibe-api` | Mistral, general API key | `vibe_api_general_key` | EUR 25.50 a month |
| `vibe-study-api` | Mistral, general API key | `vibe_study_api_general_key` | EUR 12.75 a month |
| `opencode-go` | OpenCode Go, through LiteLLM's own `opencode_go` provider | `opencode_go_api_key` | subscription; LiteLLM prices each request from its catalogue |
| `openrouter` | OpenRouter, free ids only, public work only | `openrouter_api_key` | free |
| `local` | OpenAI-compatible server on the GPU workstation, behind its keyed gate | `local_llm_api_key` | free |
| `google` | Google AI Studio, free tier | `google_api_key` | free tier |
| `anthropic` | Anthropic | `anthropic_api_key` | pay per token |

Planned routes: [docs/free-inference.md](docs/free-inference.md) lists every free inference source worth using (permanent or renewing tiers only), with accounts, limits, how each plugs into this proxy, whether LiteLLM tracks it, and whether it needs a harness of its own.

The four Mistral accounts are listed and probed separately because their model sets differ. A route whose key is unset or empty is skipped silently, so the sync runs before every key is written.

**Credentials.** `credential_list` holds one entry per account: `credential_name` (the route), `credential_values` (`api_key` and, except for Google and Anthropic, `api_base`) and the required `credential_info: {}`. Every value is an environment name (`os.environ/<NAME>`), never a value. A deployment names its entry with `litellm_params.litellm_credential_name`. LiteLLM sends **no credentials at all** when that name does not resolve, so `tests/config.test.mjs` fails on a dangling name in either config file: that check is the guard against a silently unauthenticated deployment. Google and Anthropic are addressed by LiteLLM itself, so their credentials carry the key only.

**Wildcards.** The catch-all wildcards are `vibe/*`, `vibe-study/*`, `vibe-api/*`, `vibe-study-api/*` (all `mistral/*`), `opencode-go/*` (`opencode_go/*`) and `local/*` (`openai/*`). There is no `openrouter/*` wildcard: OpenRouter is free only, and a suffix wildcard such as `openrouter/*:free` is not verified against the pinned release, so the generated deployments are the only way to reach an OpenRouter model. There is no Zen (`opencode.ai/zen/v1`) route: OpenCode's docs say "Free-tier chat models require OpenCode; use paid models or Go from other clients." The free ids that Go itself serves (`beam-free`, `hy4-flash-free`, `longcat-2.5-free`, `iceman-contributor-free`) are reached through the `opencode-go` route.

## Telemetry

Metadata only: model, key alias, tokens, cost, latency, status. `turn_off_message_logging: true` blanks prompts and responses in every callback, and the image test sends a marked prompt and asserts the marker is absent from the logs, the exported traces and the metrics (and that traces were exported, so the absence means something).

- **Metrics.** LiteLLM's `prometheus` callback is open source in the pinned release (1.109.1): no premium-user check anywhere on its path. It serves `/metrics/` from its own process on port 4001 (`--prometheus_metrics_port`), declared as the Application's `observability.scrape`. The request and error series carry `api_key_alias`, `requested_model`, `status_code` or `exception_status`, `model_id` and `api_provider`, so the deployment that served a request is visible per request.
- **Traces.** The `otel` callback exports spans to the collector the `python` runtime profile names (`OTEL_EXPORTER_OTLP_ENDPOINT`, gRPC).
- **Dashboard.** `deploy/dashboards/litellm.json` (spend, tokens, latency, errors and budget per key and model) ships with the Project. The alert rules live with the monitoring stack, in estate `platform/observability/rules/litellm.yaml`.
- **Requested tier against the serving deployment.** `litellm_tier_served_total` (callback `config/tier_telemetry.py`, shipped in the image as `/app/tier_telemetry.py` and named in `callbacks`) counts each served request by `requested_group` (the five tiers `tier-free`, `tier-vibe`, `tier-go-cheap`, `tier-strong-open` and `tier-review` as is, any other `tier-` name as `tier-other`, `<route>/*` for a route, `canonical` for a bare name: bounded, so a client cannot mint a series per name), `api_key_alias`, `api_provider`, `model_id` (the serving deployment), `priced` (an explicit `input_cost_per_token`/`output_cost_per_token` on the deployment decides, zero meaning free even if the cost map prices the id; with none declared, a charged request or a cost-map price means priced) `fallback` (the router retried or fell back first) and `outcome` (`success`, or `failure` for an errored attempt, so a free request that reached a priced deployment and failed there is still visible). LiteLLM's own series already carry `requested_model`, `model_id` and `api_provider`, but not price or fallback, which is why the callback exists. The same record goes into the spend log at `metadata.spend_logs_metadata.tier_telemetry`, with the unbounded `requested_model`. `tests/telemetry.test.mjs` forces a failover with LiteLLM's mock testing inside the image.
- **Paid-leak alert.** `LiteLLMFreeTierPaidLeak` (`deploy/alerts/litellm-tier.rules.yaml`, tested with `promtool test rules` by `tests/alerts.test.mjs`) fires when a request to `tier-free`, `free/*` or another free route, or from a `free@`/`openrouter@` key, is served by a priced deployment (an increase over 10 minutes, or a series that appeared in that window, since a new series starts at 1 and `increase()` alone would miss it). The estate owns the rules: copy the group from `deploy/alerts/litellm-tier.rules.yaml` into estate `platform/observability/rules/litellm.yaml`. CI validates `deploy/litellm.project.yml`, `deploy/env` and `deploy/dashboards` by path, so the extra directory does not affect it (also checked: `deploy-kit validate deploy` accepts it). The `public` key is excluded: its `public/<canonical>` groups end in paid deployments by design.
- **A price caveat.** A budget only counts what LiteLLM can price. A model it has no price for records spend 0, so a cap does not bite on it; the alert `LiteLLMSpendBlind` fires when a paid key moves tokens and no spend.

## The model catalogue and generated routing

`catalog/sync.py` runs hourly (minute 17) as the `litellm-catalog` scheduled Process. It lists what each account's provider offers, probes what the account can use, builds the routing plan, and opens a pull request with it. It never writes to the live proxy and needs no master key.

- **Listing, public catalogue and traffic; no timed probe.** A test chat request spends a free tier's daily quota, so the sync sends none by itself (`--probe <route/model>` sends one, for debugging). Each account's provider list is read with that account's own key (a free call), and a model's state comes from: (1) the listing (chat, free, served, retired: Naga `kinds` and `availability.status`, Routeway `available` and `endpoints`, Requesty `api`, Kilo `isFree`, price and dates); (2) models.dev (`https://models.dev/api.json`), matched by id inside the route's own provider named in `catalog/routing.json` `reference`: not chat, deprecated, cost 0 (free, only where the listing prices nothing above zero) and Inferbase's price; no catalogue or no match changes nothing, so nothing becomes free by absence; (3) real traffic through the proxy, read from its own Prometheus series (`TRAFFIC_PROMETHEUS_URL`, optional): served requests make a deployment `usable`, 401, 403 or 404 make it `blocked` while that evidence is inside the 7-day window; (4) the answer already recorded. Otherwise a listed free chat model is `usable` with `metadata.verified_by: listing`. Z.ai stays on `free_ids` (its free ids are not all of its list), and an approved id the list omits is `pending` until traffic or a manual probe. Statuses: `usable`, `blocked`, `unknown`, `budget-exhausted`, `error`, `not-chat`, `unprobed`, `pending`.
- **Generated config, not a database.** The plan is written to `config/models.generated.yaml` in this repository and opened as a pull request from the `bot/model-catalog` branch. The proxy reads that file from the image, so a route changes only when the pull request is merged and the image is redeployed. The pull request is titled `fix(models): refresh the generated model deployments`, so merging it cuts a patch release (release-please does not release on `chore`). Nothing is stored in the proxy's database and the admin API is not used: `store_model_in_db` is gone.
- **One deployment per (canonical model, account).** Each carries `model_name` (the canonical group), `litellm_params` (`model` as `<prefix>/<upstream id>`, `litellm_credential_name`, `order`, `weight`, `max_budget` with `budget_duration`, `cooldown_time`) and `model_info` (`id` as `<route>/<upstream id>`, `route`, `canonical`, `mode` for a non-chat model, `access_groups`, and `health_check_model` where a wildcard names one). A model is dropped once its provider has not listed it on two consecutive runs, or two consecutive probes found it `blocked` or `unknown`; `error`, `budget-exhausted`, `pending` and `unprobed` never remove one (no flapping).
- **Modality.** `mode` is `embedding`, `ocr` or `audio_transcription`; a group never mixes modes, so a model whose mode differs from its name-mates gets the group name `<canonical>:<mode>`. Non-chat models come only from the general Mistral API keys (`api_only_routes`).
- **Exhaustion.** Vibe answers 402 (`billing_vibe_budget_exhausted`) when its pool is spent. LiteLLM maps 402 and 429 to `RateLimitError` and cools a deployment down for its `litellm_params.cooldown_time` (default 5 s), but **not** in a group of exactly one deployment unless `model_info.allowed_fails_policy` carries an explicit `RateLimitErrorAllowedFails` entry. So every deployment that has a cooldown in `catalog/routing.json` and sits alone in its group gets `{"RateLimitErrorAllowedFails": 0}`. That is why the cooldowns are long (an hour for the Mistral accounts): a spent plan steps aside for the next tier instead of failing the request.
- **Anthropic's 400.** Anthropic answers an exhausted limit with HTTP 400, a `BadRequest`. There is deliberately no `BadRequest` policy: cooling on every 400 would cool Claude on any malformed request. The 400 passes through to the caller with Anthropic's own text.
- **Google is a public free tier.** The AI Studio key is a free-tier key whose prompts Google may train on, so it is only for public work. Its chat models (with evidence: models.dev or the owner's approval) join the `free/<model>` groups like any free route, with the access group `free` alone; the normal `<canonical>` group never contains `google`, and there are no `public/` or `google-free/` groups any more (owner, 2026-11-26). From 2026-12-01 Google bills `gemini-2.5-pro` and `gemini-2.5-flash` at the re-routed rates, so `free_exclusions` in `catalog/routing.json` keeps both out of every free group; `gemini-2.5-flash-lite` stays.
- **OpenRouter is free only.** Only ids whose metadata says free are ever deployed, with `extra_body {"provider": {"data_collection": "allow", "allow_fallbacks": false}}`. There is no paid OpenRouter fallback. Training is allowed because the route is public work only: most free endpoints exist only with training on, and with `deny` they answer 404 "No endpoints found matching your data policy". The OpenRouter account's privacy setting "Free model training" must be on as well.
- **Free groups: `free/<model>`.** One model on every free provider at once: `free/glm-4.7-flash`, `free/gpt-oss-120b`, `free/gemma-4-31b-it`, `free/nemotron-3.5-lightning`. A key holding the access group `free` calls the name; the proxy picks a copy whose provider is not limited now (per-deployment `rpm`/`rpd`/`tpm`/`tpd` enforced by LiteLLM, shared provider budgets, concurrency and limits learned from `Retry-After`, 402s and `x-ratelimit-*` headers kept by `config/free_limits.py`), skips limited ones without sending them a request, takes them back at reset, and never reaches a paid deployment. How ids are matched, the order, and the limits table with sources: AGENTS.md, Free groups.
- **Free models are reachable only as `free/<model>`** (owner, 2026-11-26). A free-tier provider may train on the prompts, so every free copy (OpenRouter `:free` ids, the other free-only routes, OpenCode Go's `-free` ids, the Google free tier) is public work only: it is in no `canonical` group and in no other group, carries the access group `free` alone, and no paid deployment is behind it. There are no `openrouter/<x>`, `<route>/<x>` free, `opencode-go-free/<x>`, `google-free/<x>` or `public/<x>` groups, and no `<route>-free-public` access group on a free deployment. Inferbase, which bills a dollar allowance, keeps its own `inferbase/<x>` group and `inferbase-free-public` only (never `free`). OpenCode Zen's own free models are not reachable: Zen refuses them to any client but OpenCode itself (`FreeUsageLimitError`).
- **OpenCode Go** lists extra fields: an item may carry `canonical_id` such as `zhipuai/glm-5.3`, which is stored as `metadata.canonical_id` and used for that route's canonical name (vendor segment dropped) before the alias table. The sync lists `https://opencode.ai/inference/go/v1/models`, which names every Go model with the API family it is served on (`chat-completions`, `responses`, `messages`, `generate-content`) and that family's base; both are stored as `metadata.api` and `metadata.api_base`, and the probe uses them. The proxy has no OpenCode Go base: the deployments use `opencode_go/<id>`, and LiteLLM picks the family per model from its catalogue, so a request is priced and shown under OpenCode Go. `OPENCODE_GO_API_BASE` is set for the sync only: in the proxy it would send every model to one family's base.
- **No rate limits.** No `rpm` or `tpm` is set on any deployment: a burst is served by the tier's weighted share, and a 429 cools the deployment down to the next tier.
- **The overview.** The same run publishes `README.md` beside `model-catalog.json` in the private `JorisJonkers-dev/litellm-model-catalog`: a summary per route (listed, usable, blocked, other), the canonical groups with their deployments in order, the usable models per route (free flag, context length, last probed, group) and the unavailable ones with the provider's reason, committed only when the content changes. The `local` route lists nothing while the GPU workstation is off or a game holds its GPU; the overview says so.
- **Free-route candidates.** For the static-list routes (`free_ids`) the run also records every id the provider lists with its price and free signals, and shows them in the overview and the models pull request body; nothing is deployed until the owner adds the id to `free_ids`. To approve one: read the "Free-route candidates" section of the latest models pull request, add the ids to `free_ids.<route>` in `catalog/routing.json`. Details are in AGENTS.md (Approving a free id).

Published: ids, classification, reason text, free flag, context length, group and probe times; never a key, a prompt or a response body. The format of `model-catalog.json` follows the Hermes model-catalog schema that `JorisJonkers-dev/openrouter-model-catalog` generates (`version`, `providers.<route>.models[]` with `id`, `description: "free"` and `metadata`). `python3 catalog/sync.py` writes `model-catalog.json` and `model-overview.md` locally instead when `CATALOG_REPO` and `CATALOG_TOKEN` are not set.

Probe cost bound: each probe is about 8 input and at most 16 output tokens (doubled only for a provider that demands a higher minimum), once per model per day, at most 250 a run and 30 free OpenRouter models a run; free and local models cost nothing.

## Canonical models and routing

Agents ask for one canonical name per model (`mistral-large`, `devstral`, `gemini-2.5-pro`, `claude-sonnet-4-5`, `glm-5.3`); the `<route>/<id>` names keep resolving through the wildcards. The sync builds one LiteLLM model group per canonical name from `catalog/routing.json`: the deployments are the accounts whose probe says they serve the model (`usable`), ordered by which account serves it, not by model family.

| Order | Route | Weight | Used for |
|---|---|---|---|
| 1 | `local` | 1 | models the GPU host serves, when it is reachable |
| 2 | `google`, `anthropic` | 1 | Gemini (only in a `public/*` group); Claude (only here, never any other route or a free deployment) |
| 3 | `vibe` : `vibe-study` | 2 : 1 | every model the Vibe plan serves (Mistral, and GLM or DeepSeek when the probe shows the plan serves them) |
| 4 | `opencode-go` | 1 | models neither Vibe plan nor Anthropic serves |
| 5 | `vibe-api` : `vibe-study-api` | 2 : 1 | the general Mistral API keys: the last resort, only for models no other route serves (the API-only ones: audio, OCR, embeddings and the rest of the broad list) |

Free routes are not in these groups at all: they are only in `free/<model>` (above). `local` is a normal tier. Orders are renumbered per group, so a model served only by OpenCode Go has order 1. `backup_only` keeps OpenCode Go out of a group a Vibe plan or Anthropic serves, and keeps the general Mistral API keys out of any group another route serves in the same mode: their budget is small and kept for the models only they carry, so a chat model never falls back onto them when the plans run dry (it fails instead, or a caller names `vibe-api/<id>` on purpose). `exclusive` keeps `^claude` on `anthropic` alone.

**Budgets cap each paid account once.** `accounts` in `catalog/routing.json` names every paid account, the routes that bill it, its `max_budget` and its window: `vibe` 255, `vibe-study` 127, `vibe-api` 25.5 and `vibe-study-api` 12.7 per calendar month from the 1st (UTC; the two `-api` windows are assumed to match their parents), `opencode-go` 40 per 30-day cycle anchored on its subscription (cycle from 2026-11-04 10:41 UTC, next reset 2026-12-04 10:41 UTC), `anthropic` 90 per 30 days, `inferbase` 0.5 per day, none for `google`. LiteLLM's own `max_budget` is a counter per deployment, so a route with N models could spend N times its cap; the cap is now enforced by `config/account_budget.py`, a callback named in `config.yaml`'s `callbacks`: every deployment of an account (each model, the `vibe-tier/` and `opencode-go-tier/` copies, and the route wildcard) carries `model_info.account`, the callback adds each call's `response_cost` to the account's counter and takes the account's deployments out of the pick once the counter is at the cap (a call with none left fails with the router's budget error, so fallbacks go on as before). Windows are the declared ones (calendar month, or anchored cycle), computed by `window_start()` in `catalog/sync.py`. The counter is in the proxy's memory and, after a restart, is seeded once from the spend log (`LiteLLM_SpendLogs`, summed per `model_id` since the window start); with no database, or when the query fails or takes over 5 seconds, requests are never held up and it counts in memory, retrying the seed after a minute (the spend log lags by its flush interval). Each deployment also keeps LiteLLM's own `max_budget`/`budget_duration` as a per-deployment backstop. Each deployment keeps its own `model_info.id` (`<route>:<upstream id>`, not `<route>/<upstream id>`: the router resolves a model name equal to a deployment id to that one deployment and skips every pre-call filter for it), so cooldown and failover stay per deployment. `vibe-api` and `vibe-study-api` are separate accounts with their own caps, not sub-limits inside `vibe` and `vibe-study`. The provider still enforces the plan limit.

How LiteLLM v1.108 does it (read from its source): deployments sharing a `model_name` form a group; `order` picks the lowest level first and the router falls back to the next level when the level fails or is cooled down; a 402 or 429 cools a deployment down for its own `cooldown_time`; inside a level `weight` is a request-share pick (2:1 is a ratio of requests, not of spend); `max_budget` with `budget_duration` caps a deployment's spend and takes it out of the pick with `router_budget_limiting`. `router_settings` therefore holds only `optional_pre_call_checks: [router_budget_limiting]` and `num_retries: 2`: the cooldown and the allowed-fails policies are per deployment, in the generated file. Every request's serving deployment is in the spend log (`model_id`, `custom_llm_provider`, `api_base`) and on the request and error metrics (`model_id`, `api_provider`).

Canonical names come from one explicit mapping: normalisation (lower-case, vendor prefix, `:free`, `-latest`, a trailing version stamp are stripped) plus the `aliases` table in `routing.json`. Two ids that still differ are two models; nothing is merged by a fuzzy guess. The overview's `Possible duplicates (not merged)` section lists ids that look alike on different routes, so an alias can be added.

**Rollback.** Revert the generated-config pull request (or set `config/models.generated.yaml` back to `{"model_list": []}`) and redeploy the image: the wildcards then serve every `<route>/<id>` name as before, and canonical names stop resolving. Stopping the `litellm-catalog` Process stops new pull requests. Nothing has to be deleted from a database.

## Deployment

`deploy/litellm.project.yml` is the deploy-kit Project Intent: Project `litellm` in `litellm-system` at `litellm.jorisjonkers.dev`, with its environment in `deploy/env/litellm/base.env` and its secrets at `secret/data/platform/litellm` (`master_key`, `salt_key`, `vibe_api_key`, `vibe_study_api_key`, `vibe_api_general_key`, `vibe_study_api_general_key`, `opencode_go_api_key`, `openrouter_api_key`, `google_api_key`, `anthropic_api_key`, `catalog_publish_token`, `catalog_pr_token`, and the optional free-provider keys of both waves, e.g. `groq_api_key` and `neosantara_api_key`; see `deploy/litellm.project.yml`). Settings that are not secrets are optional Vault fields in the same path too, mapped to env names in `deploy/env/*/base.env`: `cloudflare_account_id` (`CLOUDFLARE_ACCOUNT_ID`), `bazaarlink_api_base` (`BAZAARLINK_API_BASE`), `cohere_api_base` (`COHERE_LIST_BASE`, catalogue Process only: the OpenAI-compatible base the sync lists and probes; LiteLLM reads `COHERE_API_BASE` for cohere_chat, so the proxy gets none), `watsonx_api_base` (`WATSONX_API_BASE`, with `WATSONX_URL` as the same value) and `watsonx_project_id` (`WATSONX_PROJECT_ID`). A route whose field is empty is skipped with one route error naming the field. The catalogue Process gets the provider keys and both tokens; the proxy gets the provider keys only. CI validates both with the deploy-kit release `tools/deploy-kit` pins:

```bash
cd tools/deploy-kit && NODE_AUTH_TOKEN="$(gh auth token)" npm ci --ignore-scripts
npx --no-install deploy-kit validate ../../deploy/litellm.project.yml ../../deploy/env ../../deploy/dashboards
```

`salt_key` encrypts the upstream keys stored in the database. Never change it once virtual keys exist.

## Tests

```bash
npm test                                          # config checks, then builds the image and starts it
IMAGE=ghcr.io/jorisjonkers-dev/litellm@sha256:<digest> npm test   # tests an existing image
```

The image tests need Docker. They start the proxy read-only with only the project file's `writablePaths` writable, and point every upstream at a stub: they check wildcard routing and per-route credentials, the models list, the metrics and that no message text is logged. `npm run test:catalog` runs the catalogue sync's tests without Docker.

## Releases

release-please keeps a release PR from conventional commits. Merging it tags `vX.Y.Z`; the tag publishes a multi-arch image, reads it back by digest, runs the image tests against it, and publishes the Intent Fragment the estate composes. The LiteLLM version the image ships is recorded as the images lock's `version`.
